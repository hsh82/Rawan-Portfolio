# Easy Content bilingual authoring plan

Status: approved for planning only; not implemented.

Date: 2026-10-29

## Goal

Treat an English/Persian article as one logical content entity. Edit both languages on one page, keep common article settings in one place, publish both translations atomically, and make Visual mode a faithful read-only preview while Source mode owns all authoring and insertion controls.

This plan preserves the public routes (`/{locale}/blog/...`), the canonical `content/` boundary, MDX components, RTL behavior, static generation, and the development-only Easy Content security boundary.

## Confirmed problems in the current implementation

1. `content/blog/en/...` and `content/blog/fa/...` are separate directory trees. The relationship between them exists only through repeated frontmatter and `translationId`.
2. The editor reads and saves only one locale at a time. EN/FA controls are links that reload the editor with `?locale=en` or `?locale=fa`; they are not editor tabs and cannot retain unsaved work in both translations.
3. Project publication is circular. Publishing the current overview refuses while the other overview has `draft: true`, but a successful save updates only the current overview. This produces the reported EN/FA draft deadlock.
4. A project `Save draft` operation sets the project registry's `visible` field to `false`. Editing an already published project can therefore unpublish it implicitly.
5. The Draft checkbox is presented as editable state, but save behavior is controlled by which Save/Publish button was clicked. Changing the checkbox itself does not control the persisted status.
6. Project revisions hash the registry plus only the current locale overview. A change to the other translation is outside that conflict boundary.
7. The content tree is locale-specific, so missing or mismatched translations can look like different entities rather than one incomplete entity.
8. Shared fields are duplicated in localized frontmatter. Slug, category, parent project, dates, tags, featured state, and translation identity can drift.
9. Project title/description handling has two competing sources: the project registry and localized overview frontmatter. The current synchronization can overwrite an edited source title with the registry value.
10. Visual mode is sometimes `contentEditable` and converts edited HTML back to Markdown with a lossy converter. Lists, tables, links, code fences, images, MDX components, and formatting can be damaged.
11. The formatting and Insert controls remain visible in every mode and mutate the hidden Source textarea even while Visual or Diff is selected.
12. Visual preview uses a small hand-written Markdown renderer. It does not faithfully render the production MDX component map; advanced blocks are reduced to placeholders or force a partial read-only state.
13. Validators, route helpers, link checks, build verification, and the content creation script all assume the locale is the first path segment below `content/blog`.

## Target content model

Use one directory per logical document, with one shared metadata file and one lossless MDX body per language:

```text
content/blog/
  landing/
    entry.json
    en.mdx
    fa.mdx
  projects/
    <project-id>/
      overview/
        entry.json
        en.mdx
        fa.mdx
      articles/
        <article-slug>/
          entry.json
          en.mdx
          fa.mdx
```

This is one post/entity in `content/blog`, not two English/Persian blog trees. The two MDX body files remain separate because they have different prose direction, typography, word order, embedded labels, and potentially localized media alternatives. A single monolithic bilingual MDX file is not recommended: it would complicate Astro compilation, source editing, RTL rendering, translation routing, and conflict resolution without improving the editing experience.

### Shared `entry.json`

Common settings live once:

- stable entity ID and translation ID;
- slug and parent project ID;
- kind (`landing`, `overview`, or `article`);
- category/subcategory;
- publication status (`draft` or `published`);
- publication and update dates;
- tags, author, table-of-contents flag, and featured state;
- cover/media reference;
- optional ordering and relationship IDs.

Localized MDX frontmatter contains only localized values that genuinely differ, such as title, description, cover alternative text, and optional localized SEO fields. The body remains full MDX. During migration, compatibility frontmatter may be generated by the loader, but duplicated shared fields must not remain independently editable sources of truth.

Project portfolio metadata such as maturity, technologies, icon, role, favorite state, and confidentiality class remains in the canonical project record. The blog entity references the project by stable ID. Publication commands update the project visibility and its overview status in one transaction when that relationship requires it; they must not maintain two unrelated status controls.

## Publication behavior

1. A new entity starts as one shared `draft`, with EN and FA marked incomplete until their required localized fields exist.
2. `Save draft` writes shared settings and both language buffers transactionally. It never requires either translation to be publishable.
3. Opening or saving an already published entity does not automatically turn it into a draft or hide its project card.
4. For a published entity, the normal save label becomes `Save changes`. Explicit `Unpublish` is a separate confirmed action; it is never a side effect of editing.
5. `Publish` validates shared settings, EN, and FA from the same editor state. Validation errors identify the exact General/EN/FA tab and field.
6. Publish is all-or-nothing: both bodies, shared metadata, and related project visibility are written in one rollback-capable transaction.
7. Locale completeness is diagnostic state, not separate publication state. There is no independently published EN draft and FA draft for the same entity.
8. The combined revision covers `entry.json`, `en.mdx`, `fa.mdx`, and any project registry record updated by the operation. A conflict response identifies which slice changed and preserves the user's unsaved buffers.

The initial implementation will not add a CMS-style staged revision that keeps an old published version live while a newer draft is saved. Saving changes to a published canonical entity means those changes are included in the next build. Adding parallel published/draft revisions would be a separate feature.

## Editor information architecture

### One editor page

The editor route identifies the logical entity, not a locale. Locale query parameters may be accepted temporarily as a migration redirect, but are not part of the final identity.

```text
/dev/content/edit/project/<project-id>/
/dev/content/edit/article/<project-id>/<article-slug>/
```

The API returns one aggregate payload:

```text
entity
  shared
  locales.en
    metadata
    source
    revision
  locales.fa
    metadata
    source
    revision
  combinedRevision
```

### Tabs

- `General`: shared article settings, publication state, parent, dates, tags, cover, icon/project settings where applicable, and relationship fields.
- `English`: English title, summary, localized media text, and complete English MDX source/preview/diff.
- `فارسی`: Persian title, summary, localized media text, and complete Persian MDX source/preview/diff.

Switching tabs is local UI state and never reloads the page. Each language tab shows its own dirty/completeness/error badge. Recovery storage is keyed by entity and stores General, EN, and FA together.

### Source, Visual, and Diff

- Source is the only editable body surface.
- Formatting, block insertion, media insertion, drag/drop, and paste-to-insert controls are shown only in Source mode.
- Visual is always read-only and contains no add/edit controls.
- Visual uses the same MDX component map and styling as the public article reader, rendered through a development-only preview endpoint or isolated preview frame. Mermaid, Markmap, Figure, Callout, CodeBlock, math, tables, links, and images must render as they do on the site.
- Preview compilation errors are displayed without mutating source.
- Diff can switch between General, EN, FA, and All changes. It never reconstructs MDX from rendered HTML.
- Source text remains LTR for predictable code editing; Persian Visual output and localized metadata fields use RTL.

## Backend and loader changes

1. Replace locale-first path helpers with logical entity resolvers that map an entity ID to shared metadata plus both body files.
2. Replace locale-specific `readEntity`/`saveEntity` payloads with aggregate bilingual reads and transactional writes.
3. Replace per-file draft logic with one shared status and explicit locale-completeness validation.
4. Introduce a loader adapter that emits the same two Astro collection entries expected by the public site—one EN and one FA—from each logical entity folder.
5. Keep generated collection IDs stable enough that public route output remains unchanged. Route construction should use normalized entity metadata rather than parsing a locale-first filesystem ID.
6. Update article lookup, translation switching, category archives, project overview/children discovery, RSS, sitemap, Pagefind, and previous/next navigation to consume normalized fields.
7. Update project overview validation to check one logical overview entity with two complete locales and a shared published status.
8. Keep all write APIs loopback-only, token-protected, development-only, path-safe, symlink-safe, and rollback-capable.

## Migration plan

### Phase 1 — contract and fixtures

- Add tests that reproduce the current circular draft failure and accidental unpublish behavior before changing implementation.
- Define and schema-validate `entry.json` and the aggregate editor API.
- Add representative fixtures for landing, project overview, child article, advanced MDX, missing translation, and published content.

### Phase 2 — bilingual adapter

- Implement logical entity discovery and aggregate reads while retaining read-only compatibility with the old locale-first layout.
- Add combined revisions and transactional EN/FA/shared writes.
- Implement the new save, publish, and explicit unpublish state machine.

### Phase 3 — editor UX

- Replace locale navigation links with General/English/Persian tabs.
- Keep both language buffers alive on the same page.
- Add per-tab validation and dirty indicators.
- Make insertion tools Source-only and Visual fully read-only.
- Remove HTML-to-Markdown visual saving.

### Phase 4 — faithful preview

- Add a dev-only MDX preview path using production reader components and styles.
- Isolate preview output from editor controls and keep compilation failures recoverable.
- Verify all supported custom components in both directions and themes.

### Phase 5 — content migration

- Add a dry-run migration script that pairs files by translation ID and logical path.
- Report missing translations, mismatched slugs, duplicate IDs, metadata differences, and draft mismatches before writing.
- Move each pair into one entity directory and create its shared metadata without changing public URLs.
- Refuse collisions and never overwrite unmatched files.
- Migrate the blog landing through the same model.
- Run first on fixtures, then on the owner content branch. Do not keep old and new trees as dual canonical runtime sources after migration.

### Phase 6 — consumers and cleanup

- Update the Astro content loader, public selectors, routes, link checker, content validator, build verifier, and `content:new` authoring script.
- Update the Easy Content tree to display one item with EN/FA completeness badges.
- Remove locale-first compatibility code only after migrated content passes all checks.
- Update `design/architecture/easy-content.md`, `design/architecture/content-model.md`, and `design/components/blog.md` to describe the implemented model.

## Required tests and acceptance criteria

- One editor page loads and retains General, EN, and FA changes.
- Saving an incomplete draft succeeds and writes all changed slices atomically.
- Publishing with missing data fails before any write and focuses the correct tab/field.
- Publishing complete EN/FA content succeeds once; there is no cross-locale draft deadlock.
- Saving edits to a published entity does not unpublish it.
- Unpublish is explicit and updates the overview/project relationship consistently.
- A conflict in General, EN, or FA is detected by the combined revision without losing local edits.
- Visual mode cannot mutate content and exposes no insert controls.
- Source insertion still supports all registered blocks and media.
- Visual preview faithfully renders ordinary Markdown and all supported MDX components in EN/FA, light/dark, desktop/mobile.
- Migration dry-run reports inconsistencies and is idempotent after a successful migration.
- Existing article URLs, translation links, category pages, RSS, sitemap, search indexing, project cards, and article navigation remain stable.
- Draft content does not generate production routes and Easy Content code does not leak into production output.
- `npm run content:validate`, `npm run content:check-links`, `npm run check`, `npm run test`, and `npm run build` pass after implementation.

## Scope boundaries

- No application or content migration is performed as part of this planning step.
- No public URL redesign.
- No rich WYSIWYG editor or round-trip HTML-to-MDX conversion.
- No automatic translation.
- No commit, push, or deployment until explicitly requested after implementation and verification.

## Recommended implementation order

Implement the data contract and tests first, then the aggregate adapter/publication state machine, then the tabbed editor, then faithful Visual preview, and only afterward migrate real content and remove compatibility code. This keeps the existing site buildable throughout the change and addresses the publication deadlock before visual polish.
